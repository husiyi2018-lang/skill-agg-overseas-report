## 一、HTML 生成

### 1. ⚠️ 最常犯：追加 CSS 落到了 `</style>` 外面

```python
# ❌ 错误 —— 新规则落到 </style> 之后
h = h.replace('</head>', CSS)
# 结果：浏览器把样式表当正文渲染，报告顶部出现一整段裸 CSS 文本

# ✅ 正确
h = h.replace('</style>', CSS + '</style>')
# 或
i = h.rfind('</style>'); h = h[:i] + CSS + h[i:]
```

**这个坑在 DramaBox 报告里连犯两次。** 改完**务必校验**：
遍历 head 内所有 `选择器{...}`，确认每条的起始位置都落在某个 `<style>...</style>` 区间内。

→ 现在直接跑 `scripts/validate.py`，它会检查。

### 2. `--brand-l:#f0b martial;` 这类脏值

COC 报告的 gold 主题块里有这行（COC theme 生成时的笔误），
虽然后面有正确覆盖所以没出问题，但属于垃圾。**`themes.md` 里的版本已清理。**

### 3. 重复的 `<script>` 段

COC 报告的灯箱 script **完整出现了两次** —— 冗余，会重复绑监听。
（`shell.html` 已合并成一段。）

### 4. 静态 `<title>` 要单独同步

运行时的 JS 可能改写 `document.title`，但**导出 PDF、书签、搜索结果读的是静态标签**。
用模板生成时记得一起替换 `{{TITLE}}`，否则留成模板默认标题。

### 5. `.mmtree li::after` 的横线位置固定

横线画在 `top:16px`。**`mm-l2` / `mm-l3` 的文字如果换行，横线会落在文字中间**。
→ 宁可多写几条短的，也别写一句长的。

### 6. `esc()` 不存在

报告是手写 HTML，**不做任何转义**。
- 要写字面尖括号请用 `&lt;` `&gt;`
- 属性值里的引号用 `&quot;`（`data-title` / `data-sub` 尤其容易踩）

### 6b. 封面容器必须同时支持 `<img>` 和 `<video>`

`.mcover` / `.gal-thumb` / `.hookthumb` / `.tplthumb` / `.sc-thumb` 这 5 个容器，
**最初只写了 `.xxx video{...}` 规则**。当素材视频超预算走「封面兜底」时放的是 `<img>`，
没有规则 → 图片按原始尺寸溢出容器，卡片被撑破。

**已修**：shell 里补了 `.mcover img,.gal-thumb img,...{width:100%;height:100%;object-fit:cover}`。
**自己在 shell 外加新容器时，记得 video / img 两条都写。**

（这是冷启动验收时发现的 —— 用真实数据跑一遍的价值就在这。）

### 6c. Python `%` 格式化模板里的字面 `%`

用 `"""...""" % (...)` 拼 HTML 时，正文里的**字面百分号必须写成 `%%`**。
漏掉的报错是 `ValueError: unsupported format character '<' (0x3c)` ——
报错位置指向后面的 HTML 尖括号，**很难看出真正原因是前面一个裸 `%`**。

→ 推荐直接用 `.format()` 或 f-string，或在拼接前先跑一遍转义检查。

### 32. ⚠️⚠️ 容器标签不配平 —— **唯一一类「其余闸门全绿也拦不住」的失效**

**症状**：报告上半部分完全正常，从某一处起排版崩掉 —— 侧栏消失、正文占满屏幕。
打开控制台没有任何报错，页面还是"能看"的，所以很容易被当成"浏览器的问题"。

**根因**：正文里多了闭合标签，把 `.layout`（`display:flex`，侧栏 300px + 正文）**提前闭合**。
从那一刻起，后面的内容全部渲染到弹性布局**外面**，成为全宽块级流 —— 侧栏没了、正文铺满。
崩点正好落在第一个多余闭合标签处，所以表现为「下半部分坏了」。

**实测案例**：组装脚本在「素材族」循环里写了两个 `A('  </div>')`，一个关 `.mgrid`、
一个误关 `.fam`；而 `.fam` 本该在循环结束后统一关闭。6 个素材族 → 多 6 个 `</div>`，
和实测的「222 开 / 228 闭，差 6」完全吻合。

**为什么必须单列一条**：`fidelity.py` 管数字、`check_material_cards` 管卡片、
`check_nav` 管锚点 —— 这些**全都是绿的**。数字错会被拦，
**结构崩坏不会被任何一项拦下**。这是验证体系里唯一的盲区。

**查法**（`validate.py` 的 `check_tag_balance` 已内置）：

```bash
python scripts/validate.py <报告.html> --dir <工作区>   # 看 [err] 14
```

它做两件事，缺一不可：
- **总数相等** —— 不等就说明有错；
- **逐标签累计深度不得跌到负值** —— 总数不等只能告诉你"有错"，
  跌负能直接指出**第一个**多余闭合标签的偏移与上下文，定位成本从"通读全文"降到"看一行"。

**只统计结构性容器**（div / main / nav / section / details / table / ul / ol）。
行内标签（span / a / b…）在 HTML5 里允许隐式闭合，查了全是假阳性。

**写组装脚本时的防线**：重复区块（素材族、卡片墙）的**开闭配对要成对出现**，
最容易犯的就是「循环里既关内层又关外层」。写完后拿 `<div>` / `</div>` 计数对一遍再交付。

## 二、素材与体积

### 7. 封面必须先压缩再内嵌

封面是**从视频抽的首帧**（素材清单里没有封面图字段），所以 `covers.py` 依赖 ffmpeg。
原图直嵌 → 单文件 20MB+（60 张 17MB）。
压到**宽 360px / JPEG q72** → 60 张约 3.35MB base64，报告落在 2MB 出头。

### 8. 视频内嵌必须有预算

`download_url` 常是**完整长片**（几十 MB），整条内嵌会让文件爆炸。
→ **`≤2MB` 且累计不超总额度**才内嵌，超出走封面兜底。
**兜底了要在口径里写明**，否则读者以为卡片坏了。

### 9. 外链会失效

`download_url`（素材视频直链）是**有时效性**的链接，签名过期即 403。
→ **报告要能离线单发**就必须全部内嵌 base64。外链方案只在「自己看」时可用；
   链接过期后**重跑 `claw.py materials`** 换一批新链接。

> **补充（实测）**：这批链接**不只是过期才失效**，同一批次里也会**中途变 401**。
> 长任务跑到后半程才发现取不到图，只能回头重跑 `materials`。
> → **建议在第 2 步一开头就把 `materials` 拉全**，别等写正文时才补。

### 21. ⚠️ 素材卡片「静默退化」——排版正常、全绿通过，但点不动也播不了

**这是本技能最贵的一次坑**，因为它**不会报错**。

交付过一份报告，代表素材区块 14 张卡片排版整齐、ID 徽标齐全、`validate.py` 全绿，
但读者反馈：**点不动、也播不了**。两个症状、两个根因：

| 症状 | 根因 |
|---|---|
| 卡片没有跳转链接 | 卡片写成了 `<div class="mcard">` —— **裸 div 天然没有 href** |
| 代表素材播放不了 | 卡片封面是**手绘 SVG 占位图**，里面没有 `<video>`；而**第 2 步「素材实体化」压根没跑** |

**为什么会全绿**：旧校验只查了「ID 徽标在不在 `covers.json` 里」「ID 是不是 7 位 hex」。
卡片退化成裸 div + SVG，这两条**照样满足** → 校验通过 → 交付。

**正确写法**（每条都是硬要求）：

```html
<a class="mcard" href="https://appgrowing-global.youcloud.com/material/{全量ID}"
   target="_blank" rel="noopener">
  <div class="mcover">
    <video src="data:video/mp4;base64,…" muted loop playsinline
           preload="metadata" poster="data:image/jpeg;base64,…"></video>
    <button class="mplay">❚❚</button>
  </div>
  …
</a>
```

**已加机械闸门**：`validate.py` 新增 `check_material_cards()`，四条断言
（是 `<a>` / href 是全量 ID / 封面有 video 或 img / 封面无 `<svg>`）。
这四条合起来**等价于「第 2 步真的跑过」** —— 从「文档里的建议」变成硬闸门。

→ **连带教训**：`covers.json` / `videos.json` 是空的，说明媒体步骤没跑。
**空的中间产物本身就是最强信号**，第 3 步动手前先 `ls work/` 看一眼。

### 21b. 卡片 ID 必须**全量书写**，7 位只是展示

ID 是 `32 位 hex`（部分素材带 `-201` / `-202` 平台后缀）。把 ID 截成 7 位再拼链接，
会得到 `/material/dab2414` 这种**打不开的死链**，同时 `b-lang` 徽标校验也会失配。

```
✅ data-id="dab2414c8e0f4a5b6c7d8e9f0a1b2c3d-201"   （内部/链接用全量）
✅ <span class="b-lang">dab2414</span>               （只是给人看的 7 位徽标）
❌ href="…/material/dab2414"                          （链接里截断 → 死链）
```

→ 规则：**内部与链接 = 全量 ID，徽标 = 7 位 = 全量 ID 的前 7 位。**

### 21c. 卡片 ID 重复（第 N 张和第 1 张是同一个素材）

同一次组装里，第 7 张卡和第 1 张卡 ID 撞了（都是 `dab2414…`）——
多半是从清单里「挑代表素材」时手抄重了。
`validate.py` 会报「卡片 ID 有 N 个重复（违反铁律 6）」。

**还有个更隐蔽的重复**：想换掉重复项时，如果从清单里另挑一条，**要确认它是「反例」而不是又一个正面样本** ——
这次换上的 `38d662e`（带性暗示风险的素材）本来就是个**风险反例**，正好用来讲合规红线。
**重复项换掉时，顺手检查新选的这条在叙事里扮演什么角色。**

### 21d. 有的素材 ID 根本不是视频

`materials` 返回的清单里混着非视频素材（实测一条 `…-102` 后缀的其实是 **JPEG**）。
直接丢给 ffmpeg 会报错；`ffprobe` 查不到视频流时，应**降级为 image**：
把原图 base64 直接当封面，`kind="image"`。

→ `media_embed.py` 已按 `probe → 无视频流 → kind=image` 处理，别在别处硬套抽帧流程。

### 33. ⚠️ `media_embed.py` 的内嵌额度是**跨已存在的 `videos.json` 累加**的

**症状**：分批跑内嵌时，**后面几批全部走封面兜底**，日志只说
`[BIG ] … 累计将超总额度 14.0MB,走封面兜底`，看不出是"这批太大"还是"前面已经占满了"。

**根因**：脚本会读取已存在的 `work/videos.json`，把它已占的 base64 体积算进累计额度，
再判断新素材能不能进。所以**第二批的可用额度 = 总额度 − 第一批已占用**。

**实测案例**：先给 A 产品的 20 条跑内嵌（占满 13.8MB / 14MB），
再给 B 产品的素材跑 —— 即使单独给到 `--total-mb 22`，B 的素材仍然全部 `BIG`，
因为额度早被 A 占光了。表现是"报告里 9 条视频全是 A 的，B 一条都没有"。

**正确做法**：**一次性把两款/多款产品的素材 ID 合并成一个清单跑**，
让脚本自己按顺序分配额度；需要重排时先删掉 `work/videos.json` 再整批重跑。

```bash
# ✅ 一次给全，按顺序分配
python scripts/media_embed.py --dir <工作区> --ids "<A的ID>,<B的ID>,<C的ID>" --total-mb 26
# ❌ 分批追加 —— 后一批会全部兜底
```

**交付前对一眼**：`videos.json` 里各产品/各方向的条数是否**大致均衡**。
若发现全集中在某一类，就是踩了这条。

## 三、PDF 导出

### 10. Edge headless 把文件写到自己的安装目录

```bash
msedge --headless --no-pdf-header-footer \
  --print-to-pdf="C:/绝对路径/out.pdf" \
  "file:///C:/绝对路径/rendered.html"
```
**Edge 会把 PDF 写到它自己的 cwd（安装目录），不是 `--print-to-pdf` 里的路径。**
→ 转完**必须 `cp` 回目标目录**，或直接用 `scripts/topdf.py`（已处理）。

### 11. 出 PDF 一律用 `topdf.py`，别自己写 CDP

自己用 Chrome DevTools Protocol 连浏览器，在 Windows/Edge 上容易 IndexError，且要处理端口、超时、空白页。
→ **统一用 `scripts/topdf.py`**：已处理「Edge 把文件写到自己目录」的坑、超时、空白页检测、以及
找不到浏览器时跨平台自动找（Edge/Chrome，Windows / macOS / Linux 都查）。

### 12. markdown → HTML：`---` 被误判成 Setext H2

python-markdown 会把**紧跟 blockquote 的 `---`** 误判为 Setext H2 标题。
→ 转换前对 `\n---\n` 前面**补一个空行**。

### 13. PDF 里侧栏和按钮要隐藏

`shell.html` 已有 `@media print` 规则，会隐藏 `nav.side` / `#menuBtn` / `#topBtn` / `#progress`，

### 34. ⚠️ `fidelity.py` 剥离素材短 ID 的正则**要求同时含数字和字母**

**症状**：保真校验报某个 7 位纯数字串「既不在 raw 语料命中、也未在 derived.json 登记(疑似自创)」，
但那个串明明就是一张素材卡上的短 ID。

**根因**：`report_text()` 里剥素材短 ID 用的是

```python
h = re.sub(r"\b(?=[0-9a-fA-F]*\d)(?=[0-9a-fA-F]*[a-fA-F])[0-9a-fA-F]{6,12}\b", " ", h)
```

两个 lookahead 分别要求「含数字」和「含字母」—— 于是 `0932a9f`（含字母）会被剥掉，
而 `8868493`（**恰好全是数字**）**不匹配、不被剥离**，就落进了数字保真通道被判自创。

**处置**：这是**正则覆盖不到的边界**，不是编造。如实登记即可，并在 note 里写明原因：

```json
"8868493": {
  "formula": "material_short_id(8868493b00b1e1145c787a06d3d199a3-202)",
  "source": "raw/materials_all.json",
  "note": "素材短 ID，不是数据主张。该 ID 恰好全为数字，未被短 ID 剥离正则覆盖，故登记过保真通道。"
}
```

**注意区分**：**不要**为了让校验通过而把这条规则当成"万能后门"。
登记的前提是该 ID **真实存在于 `materials_all.json`**（`check_gallery_ids` 会独立核验）——
正则是漏网的，ID 是真的。两者缺一不可。

**更省事的规避**：正文里引用短 ID 时，**包在 `<i>` 里**（`<i>8868493</i>`）。
`report_text` 对 `class="b-lang"` 与 `<i>` 两类位置有专门剥离，能直接绕开这个边界。

```bash
# 只重拉那一路，落成单独文件，再并回主清单
```

### 22b. ⚠️「挂死」和「鉴权失败」长得一模一样 —— 别急着怀疑 Key

`call_aggclaw` 内置 `MAX_RETRIES=10 × REQUEST_TIMEOUT=600`，**最坏情况静默挂 100 分钟**，
最后只抛一句「已重试 10 次」。如果不做分层诊断，你会把它误判成「Key 过期了」，
然后去个人中心翻 Key、换 Key、怀疑 IP —— 全是白费。

**先跑这三条 curl，30 秒定性：**

```bash
BASE=https://ai-chat-global.youcloud.com
curl -sS --noproxy '*' -m 12 -o /dev/null -w "root   %{http_code} %{time_total}s\n" $BASE/
curl -sS --noproxy '*' -m 12 -o /dev/null -w "midw   %{http_code} %{time_total}s\n" $BASE/aichat/foobar
curl -sS --noproxy '*' -m 12 -o /dev/null -w "biz    %{http_code} %{time_total}s\n" \
  -X POST -H "Content-Type: application/json" -d '{"input":"hi"}' $BASE/aichat/claw
```

**指纹对照表 —— 症状落在哪一行，病因就在那一层：**

| `root` | `/aichat/foobar` | `/aichat/claw` | 结论 |
|---|---|---|---|
| 200 秒回 | **401 秒回** | 0 字节超时 | **该 location 的 upstream 宕机**，非你的问题 |
| 200 秒回 | **502（数秒）** | 0 字节超时 | upstream 半死/正在重启，同一病因 |
| 200 秒回 | 0 字节超时 | 0 字节超时 | 整个网关后端挂了 |
| 连不上 / 超时 | 连不上 | 连不上 | 本地网络或出口问题，才轮到查代理 |
| 200 秒回 | 401 秒回 | **401 / 403** | 这才是**真·鉴权失败**（Key 无效） |

判据很简单：**秒回的路由 = 该层活着；0 字节挂死 = 该层 upstream 死了。**

`/aichat/foobar` 是个**不存在的路径**，能秒回 401 说明鉴权中间件是好的。
既然中间件活着、而 `/aichat/claw` 一个响应头都不返回，故障就被夹在
「中间件之后、业务代码之前」这一小段里 —— **和 Key、和你无关**。

两个反直觉细节：

- **`/aichat/claws`（多一个 s，不存在）也会挂死。** 说明 nginx 用的是前缀匹配
  `location /aichat/claw`，故障是 location 级的，不是某个具体 endpoint 的问题。
- **中间件状态会抖。** 相同 URL 连续打 6 次全 401（0.7s），第 7 次可能变 502（3.9s）。
  上游是多实例，部分实例死了。**别用单次探测下结论**，至少打 3 次。

**怀疑服务端故障时，先用历史产物自证「它以前是好的」**，避免误改配置：

```bash
ls -la --time-style=full-iso raw/materials_all.json
tail -n 5 work/materials.log
```

若 `materials.log` 显示此前成功取到全量（如 `[done] -> ... (1182 条去重)`）、
且 `materials_all.json` 的 mtime 就在今天 —— 那就是**新发生的服务端故障**，
本地任何改动都不需要，等它恢复即可。**这种情况直接向用户报「服务端故障 + 证据」，
不要空转重试。**

> **给脚本的启示**：`0 字节超时`应被视为**可快速判定的硬故障**，
> 而不是「再试一次说不定就好了」。当连续 2 次都是 0 字节超时，
> 应立即中断并输出上面那张对照表，而不是把 10 次重试跑满。

### 35. ⚠️⚠️ aggclaw 提问**越轻越稳** —— 重问法的失败率是压倒性的

### 36. ⚠️ 「按产品聚合排名」这类提问，**当前接口结构性取不到**

**症状**：问「XX 品类素材量前 8 的产品及各自素材数」，要么超时，要么引擎拒绝回答。

> 「如果我直接列出 Top 8 产品 + 各自素材数，那将是无依据的编造数据……
>  所以我不这样做。」

**实测**：报告 ④ 前后发了 6 路查询，失败的 2 路**全部是**「列出前 N 款产品+素材数」；

**替代做法 —— 指定产品名，逐一取数，再自行汇总**：

```bash
# ❌ 问"前 8 名是谁"
# ✅ 点名问，每款一路
"手游 <产品名> 在 <窗口> 的素材投放总量是多少条？"
```

### 38. ⚠️ 布局探针把报告副本写进了**系统盘临时目录** → 撑爆 C 盘、全盘工具失灵

**症状**：跑了几轮无头浏览器布局探针后，`df` 显示 C 盘可用 **0 字节**；
接着连 `grep`、`python -c` 都报 `No space left on device` ——
**连 print 都输出不了**，因为 stdout 缓冲刷不出去（Python 的 stdout 是块缓冲）。

**根因**：探针（`measure_layout.py` / `find_overflow.py` / `probe_drawer.py`）
��了注入测量脚本，会把**整份报告复制一份**再交给无头浏览器。报告本身就是
**20MB 级**（base64 内嵌视频/封面），乘以「每个视口一份 × 每个脚本 × 多个视口」——
实测 **9 个文件 = 192MB**，而 `tempfile.gettempdir()` 默认落在 C 盘。

**为什么危险**：C 盘是系统盘，撑爆它的代价不是"少几个文件"，
而是**这个环境里的所有工具都开始失灵**：后台任务的输出写不进去、命令输出被截断、
报错信息本身都打印不出来（打印也要写缓冲区）。
排查时很容易误判成"脚本坏了"或"文件损坏"。

**做法**：

```python
# ❌ 落在系统盘
tmp = os.path.join(tempfile.gettempdir(), "probe_%d.html" % width)
# ✅ 落在工作区所在盘（通常是有空间的 D 盘）
os.makedirs("D:/reports/_probe_tmp", exist_ok=True)
tmp = os.path.join("D:/reports/_probe_tmp", "probe_%d.html" % width)
...
try: os.remove(tmp)          # 用完即删，别攒着
except OSError: pass
```

**更普遍的一条**：**报告是 20MB 级的产物，任何"复制它"的操作都要先想清楚副本落在哪个盘。**
批量渲染、转 PDF、生成缩略图同理。

### 39. 💡 曝光数换算成「万」会**被数字保真拦下** —— 建议直接写精确值

**症状**：保真校验报一串 FAIL：`1643.5, 1782.3, 1879.6 … 疑似自创`，
而这些数明明是从语料里的曝光量算出来的。

**根因**：语料里是 `26,457,465`，报告里写的是 `2,645.7 万`。
**数值等价，但字面不同** —— 保真器走的是字面命中 + 取值等价两条路，
而"除以 10000 再改写单位"这一步是**报告的加工**，语料里不存在 `2645.7` 这个数。

**两种处置，推荐第一种**：

1. **直接写精确值** —— `26,457,465`。既过闸，对读者也更可信；
   头部素材本来就该让人看见真实量级。
2. 确实要用「万」表述，就逐条登记进 `derived.json`，
   公式写成 `to_wan(26457465)`（**带标识符的公式会被求值检查跳过**，
   若写成 `26457465/10000` 则 `10000` 自身也要能溯源）。

**同理适用于**：环比百分比的四舍五入、把条数换算成"万条/亿条"、
把毫秒换算成秒 —— **任何"换算"都是加工，都要么写原值，要么登记。**

### 40. ⚠️ 用「区块替换」打补丁时，**替换区间盯错了标记**会静默删掉整章

**症状**：`validate.py` 报两条:
① `导航死链 1 个: sec-6`；② `报告没有 #markmap → 跳过`（脑图整个没了）。
页面打得开、上半部分完全正常，所以肉眼很容易漏过去。

**根因**：替换区块时，起点取的是 `# ---- sec-6` 这样的**注释标记**，
终点取的是下一章里的某一行。但这两者之间的范围**包含了整个 sec-6 的全部内容**
（章节标题、数据表、三受众、flow、脑图），一次 `s[:i0] + 新块 + s[i1:]` 就把它整段吞了。

**为什么会发生**：注释标记在文件里是**装饰性的**，它和"这一章从哪里开始"并不等价 ——
`# ---- sec-6` 出现在 `H2(6, ...)` **之前**，但新块本该插在 **sec-5 内部**（素材画廊的位置）。
起点取错一格，区间就从一个"插入点"变成了一段"覆盖范围"。

**做法**：
- **优先用「成对、且紧贴内容」的锚点** —— 比如 `FAM = [` → 下一个章节的 `H2(` 调用，
  而不是用脆弱的注释分隔线；
- **替换后立刻数一遍关键结构**：章节数、`#markmap` 是否存在、素材卡数。
  这三个数变了就说明区间划错了（本次就是靠 `#markmap` 消失发现的）；
- 更稳的做法是 **insert 而不是 replace** —— 在锚点前插入新块，原内容一行不动。

**为什么这次没造成交付事故**：`check_nav` 的孤儿/死链检查和脑图的 `#markmap` 存在性检查
把它拦下了。**这是验证体系该有的样子** —— 结构被删会留下痕迹，而痕迹有闸门查。

### 23. 别让模板化小标题把报告做「刻板」

`build_report.py` 里曾硬编码三个小标题：

### 24. 编码参数数字会被保真器判 FAIL

正文里写了「压到宽 **270**」「抽 **0.6** 秒那一帧」——`fidelity.py` 报 FAIL：
这两个数在 raw 语料里**命中不了**，也不是派生数据。

**根因是分类错了**：`270` / `0.6` 是**编码/抽帧参数**，不是**数据**。
保真校验只管「数字能不能溯源」，它分不清「这数字是不是数据」。

**处理**：**不要在正文里写编码参数**。读者不需要知道转码宽度是多少。
（真要写，就写进「制作口径」脚注并接受它会 FAIL —— 不值得，直接删。）

> **顺带一条**：`derived.json` **只登记数据类派生值**（占比、环比、合计）。
> 别把编码参数塞进去「洗白」—— 登记制是为了防编造，不是为了让任何数字都能过闸。

### 26. ⚠️ 脑图依赖注进了 `<style>`（或注释里）→ 脚本永不执行，静态断言照样全绿

`mindmap.py` 是靠找标记位来注入 1MB 依赖的。`shell.html` 里**写着标记位那串字的地方不止一处**
—— 实测 **3 处**，只有一处是注入目标：

```text
shell.html:287   /* ==== 10b. .mmk —— Markmap 交互脑图 ====
                    依赖(d3 / markmap-lib / markmap-view)由 scripts/mindmap.py 内联到文件末尾的
                    MARKMAP_VENDOR 标记位（正文里那处；此处刻意不写完整标记…） */   ← <style> 里 ❌
shell.html:784   <!--MARKMAP_VENDOR-->                                              ← 唯一正确目标 ✅
shell.html:789      依赖:  MARKMAP_VENDOR 处内联的 d3 / markmap-lib / markmap-view  ← 脚本体注释里 ❌
```

注 287 行与 789 行**刻意只写裸字** `MARKMAP_VENDOR`（**不**写成完整的
`<!--MARKMAP_VENDOR-->`），这样即便注入器用「全文替换」也不会误命中 —— 但**不能只靠这个**，
所以 `mindmap.py` 用 `find_bare` 找裸字，并额外做下面的位置断言。

**症状**：`document.scripts` 里没有 `mmk-d3` / `mmk-lib` / `mmk-view`；`window.markmap` 退化成
浏览器给 `<div id="markmap">` 自动创建的**同名全局**（不是库对象）；`mmk-boot` 走进
"内联依赖缺失"降级分支。而 `validate.py` 的 ③（全文搜 `<script id="mmk-d3">`）**仍然是绿的**。

**修法**（已在代码里根治，两条一起）：

1. `shell.html` 正文外**只写裸字** `MARKMAP_VENDOR`（刻意**不**写成完整注释
   `<!--MARKMAP_VENDOR-->`），`mindmap.py` 用 `find_bare` 找裸字，因此不可能命中 CSS 注释里那处
2. 注入后**自证**：断言 `BEGIN` 的 offset 不落在任何 `<style>` 区间内
3. `validate.py` 单列一条位置断言（⑦）—— 因为①③那几条**抓不到**这个失效

> 教训：**「依赖已内联」和「依赖会执行」是两件事。** 凡是"替换某个标记位"的注入，
> 都要加一条**位置断言**，别只断言内容存在。

### 27. ⚠️ vendor 内联后，静态校验会误报 → 先 `strip_vendor`

内联的 d3 / markmap bundle 是一大坨 JS，里面天然含有**看起来像我们自己的产物**的片段。
钉死前先实测，别照抄——**最初凭印象写了四条，实测只有两条站得住**：

| 断言 | 不中和 | 中和后 | 级别 | 结论 |

| `check_css_placement` body 内 CSS 规则 | 0 处 | 0 处 | — | ❌ 假声称，实测无差异 |
| autoloader 字符串 | 1 处（**块外**） | 1 处 | — | ❌ 归 #29，与 vendor 无关 |

三条实测证据：

```text
# ① d3/w3c 三个 vendor 里都没有 CSS 选择器形状
findstr /R "^[ \t]*[.#][-A-Za-z0-9_]*[ \t]*$" markmap-lib.iife.js   → 0 处

# ③ 那 1 处的位置（在 shell.html 的注释里，vendo 块外，中和动不到）

```

**两条真误报的成因**（各不相同，别混为一谈）：

```text
# check_canvas：vendor 里天然 7 处 function v( —— 正文 0 处，全是库里的压缩变量名
re.search(r"function\s+v\s*\(", h)   # 不中和 → 7，中和 → 0

# check_offline：markmap-lib 里这行，注意它**不是** src=/href= 形态，
# 所以 ERR 那条正则抓不到；污染的是「白名单外域名」的兜底 WARN
jsdelivr: (path) => `https://cdn.jsdelivr.net/npm/${path}`,
unpkg:    (path) => `https://unpkg.com/${path}`
# 不中和 → 多报 cdn.jsdelivr.net / unpkg.com / d3js.org /
#          dom.spec.whatwg.org / html.spec.whatwg.org / mathiasbynens.be / test1
```

**对策**：校验前把 `BEGIN…END` 之间**整块换成等长空格**（保留 `\n`），即 `validate.py`
的 `strip_vendor()`。长度不变 → `(?m)^` 锚点和 offset 行为不变。

**为什么只中和这一块、不抹掉全部 `<style>`/脚本体**：正文里**其它**内联脚本仍要参与扫描 ——
真把 CSS 写进 `<script>`、真引了 CDN，照样得抓得到。

> `check_css_placement` 里那句 `strip_vendor` 属于**防御性**保留（换 vendor 版本可能变），
> **不要**在文档里说成「因为有实测误报才加的」—— 实测两态皆 0。

> 注意调色板那条的修法是 `strip_vendor` **而不是** `real_tags`：`real_tags` 会把**所有**脚本体
> 一起跳过，而调色板函数本身就写在正文内联 `<script>` 里 → 变成**永不报错的假阴性**。
> 两者用途要分清：`strip_vendor` 除依赖、`real_tags` 除注释与全部脚本体。

### 28. ⚠️⚠️ 行首缩进写 `\s*` → 整条命令挂死、零输出、没有 traceback

中和 vendor 之后，那 1MB 依赖变成了**等长空白块**。任何
「行首 `\s*` 之后还要一个非空白字符」形状的正则，在那块空白上会**灾难性回溯**：

```python
# ❌ 挂死。\s 包含 \n，于是 ^\s* 从任意行首起能一路吃穿后面所有空行
re.compile(r"(?m)^\s*([.#]?[-\w]+)\s*\{")
# ✅ 行首缩进只许 [ \t]
re.compile(r"(?m)^[ \t]*([.#]?[-\w]+)\s*\{")
```

**症状极难认**：命令**零输出挂死**，没有 traceback、没有报错，
看起来像"脚本崩了"或"工具把输出吞了"，实际是**永不返回**。

**定位方法**：`faulthandler` 的看门狗是 C 层独立线程，正则回溯占着 GIL 也能把栈 dump 出来 ——
所以 `validate.py` 里挂了 `arm_watchdog()`（默认 90s，`--hang-timeout 0` 可关）。
当时最后是靠**逐函数子进程超时二分**才锁定的。

> 教训：把大块文本替换成**等长空白**（为了保 offset）很实用，但要意识到——
> 你同时**造出了一片有利于正则回溯的地形**。凡是对全文跑的正则，先想一遍它怎么对待空白。

### 29. ⚠️ 「全文搜某个字符串」在**代码里也写着的**字符串上必然翻车

这条是上面三条的**共同元坑**，在本技能里已经踩到**第四次**。

四行**全部实测过**（样本 `report-good.html`，双语言）：

| 搜什么 | 代码里哪儿也写着 | 裸搜 | 真值 | 后果 |
|---|---|---|---|---|
| `id=` + `markmap`（**引号无关**！） | `mmk-boot` 里 `d.id='markmap'`（shell.html **856 行**，**单引号**） | 1 | 1 | 只要带 boot 脚本就算「有脑图」→ 假阳性 |
| `data-mmk-fallback` | boot 的降级函数里 `el.setAttribute('data-mmk-fallback','1')` | **1** | 0 | 每份报告都被判「进了降级分支」→ 假阳性 |
| `<script …id="mmk-md-…">` 的**个数** | boot 注释里贴的示例 `<script type="text/markdown" id="mmk-md-zh"> / -en` | **3** | 2 | 被当成第 3 份 md 源，`(.*?)</script>` 一路吃到下一个 `</script>` → **完全正常的报告**被判「没有 markdown 结构」 |
| `markmap-autoloader` | shell.html **778 行**注释「刻意不用 markmap-autoloader」 | 1 | 0 | 每份报告都被判「引了 autoloader」→ 假阳性 |

> ⚠️ 第一行有个**坑中坑**：如果你只搜双引号的 `id="markmap"`，**恰好**命中不了
> `d.id='markmap'`（那是单引号）—— 于是你以为没问题，换个引号风格就翻车。
> 这类「属性断言」一律要**引号无关**（`id\s*=\s*['"]`）且**锚在开标签**上。

> ⚠️ 第四行的干扰源**不在 vendor 里**（三个 vendor 文件该串出现 **0** 次），
> 而在 `shell.html` 的 HTML 注释里 —— 所以 **`strip_vendor` 救不了它**，
> 只能靠「判用法」。别把它归到 #27。

**规则：判「用法」，不判「提及」。**

```python
# ❌ 判提及
if "markmap-autoloader" in h: fail()
# ✅ 判用法：只认真正会被浏览器加载的形态（src=/href=/import()/require()）
if re.search(r'(?:src|href)\s*=\s*["\'][^"\']*markmap-autoloader'
             r'|(?:import|require)\s*\(\s*["\'][^"\']*markmap-autoloader', h): fail()
```

**取标签/取数据源**一律走 `real_tags(h, pat)` —— 它跳过 `dead_spans`（HTML 注释 + **所有**脚本体），
只留正文里的**真标签**。

> **反向也要防**：`real_tags` 跳脚本体跳得太干净也会造成**假阴性**（见 #27 的调色板那条）。
> 所以每加一条"跳过 XX"的规则，都要补一个**负向测试**：故意造一个该报的样本，确认它真的报。

**归属判定口诀**：这条修复要用「除依赖 / 除注释 / 除脚本体」里的哪一个？
—— 取决于**你要找的东西能不能出现在那里面**。
调色板函数能出现在正文脚本里 → 只能 `strip_vendor`；
md 源标签不该出现在任何注释/脚本里 → `real_tags` 更对。
**再补一条**：若干扰源在**注释**里，`strip_vendor`（只除依赖）对它无效 —— 必须先判清干扰源在哪儿。

### 30. ⚠️ `queue` 空串行化 —— 末态 DOM 全绿，但 4 个渲染在并发跑

**场景**：语言切换要「重建容器 → 重新 transform → 重新渲染」，且并发必须串行。
写法是 `queue = queue.then(draw)`。看起来天经地义，但：

```js
function draw(lang){
  ...
  var mm = new window.markmap.Markmap(svg, opts());
  return Promise.resolve(mm.setData(root));   // ← 这个 return 是本体
}
// ❌ 漏掉 return：render() 里的 then 拿到的是**同步返回的 undefined**，
//    queue 只串住了 draw() 的同步部分，"等渲染完成"完全没生效
```

**为什么静默**：连点 4 次时，最后那次 `rebuild` 已经把 `#markmap` 换成新容器，
前三个实例在**游离（已脱离 DOM）的 svg** 上继续画 —— 页面上谁也看不见。
实测把 boot 改回 `Markmap.create`（它的内部实现是
`mm.setData(data).then(()=>mm.fit())`，**setData 的 promise 没被 return**）后：

| 判据 | 正确实现 | 空串行化实现 |
|---|---|---|
| 末态节点数 | 13 | **13**（一样） |
| 末态 `#markmap` / `svg` / `svg.markmap` | 1 / 1 / 1 | **1 / 1 / 1** |
| 末态高亮标签 | 中文 | **中文** |
| 静态自检《交互脑图齐备》 | OK | **OK** |
| **点击后第一个宏任务边界的并发渲染峰值** | **1** | **4** ← 唯一的破绽 |

**规则：末态 DOM 量不出并发，必须量"同时在跑的渲染数"的峰值。**

```js
// 在 boot **之前**注入：包一层 Markmap.prototype.setData 数在飞的数量
var cur=0,mx=0,orig=M.prototype.setData;
M.prototype.setData=function(){
  cur++; if(cur>mx)mx=cur;
  return Promise.resolve(orig.apply(this,arguments))
           .then(function(v){cur--;return v},function(e){cur--;throw e});
};
```

> ⚠️ **读点必须是"第一个宏任务边界"（`setTimeout(…,0)`），不能同 tick 同步读。**
> 同 tick 读时两个实现都还看不到渲染启动（实测都是 1，**无区分度**）；
> 到第一个宏任务边界，4 次点击已全部入队，坏实现的 4 个渲染同时起跑 → 峰值 4。
>
> ⚠️ 计量器**必须早于 boot、晚于三个 vendor 脚本**注入（`window.markmap` 要先存在）。
> 插到 `</body>` 前就比 boot 晚跑，计量器恒读 0 次调用 —— 那是最坏的一种错：
> **给出"串行化没问题"的假绿**。锚点找不到就显式退出，不许退回文末注入。

### 31. ⚠️⚠️ 无头 `--virtual-time-budget` 会**停发 rAF 帧** → 探针偶发假红，且极难自查

**症状**：同一份**正确**报告连跑 3 次，有 1 次报
「末态节点 8 ≠ 点击前 13」，采样轨迹 `13/1/1/1` → `8/1/1/1` 之后**冻住不动**。

**根因（实测钉死的）**：`--virtual-time-budget` 下渲染器**会停止派发
`requestAnimationFrame`**。在探针里给 rAF 打点计数，失败样本的计数**冻结在 2**，
之后 40 次采样纹丝不动。而 markmap-view 的 `renderData` 里正是
`await new Promise(requestAnimationFrame)` —— 渲染永远等不到恢复。

**为什么恰好是 8 节点**：EN 那棵树就是 8 个节点。所以冻住的末态不是"渲染到一半"，
而是 **EN 渲染完成（8 节点）后，`queue` 正确地挡住后续渲染、却在等一个永远不会来的帧**。
也就是说：**报"失败"的那次，恰恰说明串行化是好的** —— 红得完全颠倒。

**修法**：探针副本里先装 rAF 垫片，把帧调度换成语义等价的定时器：

```js
window.requestAnimationFrame = function(cb){
  return setTimeout(function(){ cb(performance.now()) }, 16);   // 同样是"下一帧才跑"
};
```

> ⚠️ **垫片必须早于 d3**：d3-timer 在**加载时**就把 `requestAnimationFrame` 抓进变量
> （`var setFrame = typeof requestAnimationFrame === "function" ? requestAnimationFrame : …`）。
> 晚于 d3 再打补丁，d3 用的是原生的那个 —— **垫片等于白装**。
> 所以插在 `</head>` 之前，而不是"插在 boot 之前"。

> ⚠️ **垫片会不会把真 bug 一起盖掉 —— 必须专门验证，不能想当然。**
> 实测：装垫片后把同一批判据打到「空串行化」变异体上，并发峰值仍稳定报 **4**、
> 正确实现稳定报 **1**，各 3/3 复现。**判据的区分度一分没少**。
> 凡是"为了让测试稳一点"而改环境，都要补这么一组对照。

**自检要带上"环境可信度"读数**：探针回填环境供帧计数（垫片维护的 `__mmkRAF()`），
**读不到（<0）时把"末态没收敛"降级为 WARN 而不是 FAIL** ——
分不清「报告卡住」和「环境不供帧」时，不许指控被测对象。
反过来，如果供帧计数正常（实测 58–78 次）而末态仍不收敛，那才是**真的**卡住了。

> ⚠️ 注意「并发峰值」这一条**不依赖供帧**：好实现被 `await` 挡住、后续渲染排不进来
> （峰值恒 1），坏实现的 `then` 拿到 `undefined`、4 个立刻起跑（峰值 4）——
> 帧来不来都一样。所以它不需要环境读数兜底。

**验完留下的证据链**（这套改动是这么确认的，别只信"跑起来绿了"）：

| 组 | 口径 | 样本 | 结果 |
|---|---|---|---|
| A | 末态（原样，无垫片） | 正确 | 3 次里 **1 次假红** |
| C/D | 末态（加垫片） | 正确 | 3/3 绿 |
| E | 末态 + 计量器 + 垫片 | 正确 | 3/3 绿（**计量器不是末态读不到的成因**） |
| F | 峰值 + 计量器 + 垫片 | 正确 | 峰值 **1**，3/3 |
| G | 峰值 + 计量器 + 垫片 | 空串行化变异体 | 峰值 **4**，3/3（**垫片没掩盖 bug**） |
| H | 末态 + 计量器 + 垫片 | 空串行化变异体 | **全绿**（末态零区分度） |

> 顺带纠正一条早期误判：一度以为「装了并发计量器就读不到末态」。E/H 两组证明
> **那不是计量器的性质**，而是 rAF 饥饿被更长的 promise 链放大。分开两个探针的
> 真正理由只有一个 —— **末态没有区分度（H 组）**。
